 FANFICAI - AI FANFICTION WRITING ASSISTANT
 Prototype notes, design decisions, and time estimates
 Written: 2026-07-27      Status: working prototype, verified against live OpenAI API, 25/25 tests

-------------------------------------------------------------------------------
1. WHAT THIS IS
-------------------------------------------------------------------------------
A command-line co-writer for fanfiction. You describe your story once (fandom,
pairing, rating, POV, tense, cast, tropes to avoid) and the tool keeps that
"story bible" on disk. Every generation call re-injects the bible, so chapter 12
still sounds like chapter 1 and nobody's eye colour changes halfway through.

The core insight the prototype is built around: the hard part of AI fiction is
not producing paragraphs, it is CONSISTENCY. So the design keeps persistent
structured state (JSON) and treats the language model as a stateless renderer of
that state.

-------------------------------------------------------------------------------
2. HOW TO RUN IT (no install, no API key needed to try)
-------------------------------------------------------------------------------
Requires: Python 3.10+ (tested on 3.12.10, Windows). Zero dependencies.

    cd "C:\Users\jacqu\OneDrive\Bureau\school project\AI fanfic"

    python -m fanficai init --title "The Long Way Round" ^
        --fandom "Original Sci-Fi" --pairing "Rin/Cass" --rating T ^
        --premise "Two rival couriers locked in one station for a night." ^
        --tags "slow burn,enemies to allies" --avoid "character death"

    python -m fanficai char "Rin"  --role protagonist ^
        --traits "stubborn,precise" --wants "to be believed" --voice "clipped, dry"
    python -m fanficai char "Cass" --role antagonist --traits "glib,tired"

    python -m fanficai outline -n 6           # plan six chapters
    python -m fanficai write -c 1 -w 900      # draft chapter 1
    python -m fanficai continue -c 1 -w 300 --note "raise the tension"
    python -m fanficai check -c 1             # offline lint, costs nothing
    python -m fanficai critique -c 1          # model-written craft feedback
    python -m fanficai show                   # bible + word-count dashboard
    python -m fanficai export --out fic.md

With no API key it runs on a built-in offline "mock" backend: real pipeline,
placeholder prose. For actual writing set one env var and every command upgrades
in place, no code change:

    $env:ANTHROPIC_API_KEY = "sk-ant-..."      # or OPENAI_API_KEY
    $env:FANFICAI_MODEL    = "claude-sonnet-4-20250514"   # optional

Tests:  python -m unittest discover -s tests -v      (25 tests, ~0.2s, offline)
A finished sample run is in demo/ (story.json + the-long-way-round.md).

FEATURES THAT ARE MORE THAN A WRAPPER
  * Story bible re-injection    - consistency across a long fic.
  * Chapter-seam context        - each chapter gets the last ~200 words of the
                                  previous one, so transitions don't jump.
  * Offline linter (`check`)    - deterministic, free, no tokens. Flags POV
                                  drift (ignoring dialogue), tense drift,
                                  names not in the bible, filter-verb overuse
                                  ("she felt", "he noticed"), and anything on
                                  the user's own avoid list.
  * Content guardrails          - refuses explicit content, and hard-refuses
                                  anything sexualising minors. Enforced in the
                                  engine, not just asked for in the prompt, so
                                  it cannot be prompt-injected away.
  * Provider independence       - swap models via env var; mock backend means
                                  the whole thing is testable at zero cost.
  * Spend accounting            - every call reports tokens and estimated cost;
                                  the running total is stored in the project
                                  and shown by `show`.
  * Graceful degradation        - malformed model output falls back to a usable
                                  skeleton instead of crashing.

WHAT THE FIRST REAL API RUN CHANGED (2026-07-27)
Running against gpt-4o-mini instead of the mock backend exposed four things
that offline testing could never have caught. All four are fixed:
  1. The linter's dialogue stripper treated the curly apostrophe U+2019 as a
     closing quote, so "it's" truncated the strip and leaked spoken dialogue
     into the narration check. Every chapter got a bogus POV-drift warning.
     Now only double quotes delimit dialogue.
  2. Name detection flagged every sentence-initial capital - "Great",
     "Attention", "Come" - as an off-bible character. Now a capitalised word
     only counts if it appears mid-sentence and never appears lowercase
     elsewhere in the chapter. Signal went from ~8 false names per chapter to
     one true positive: "Tess", a character the model invented in the outline
     and then used in chapter 2 without her ever being in the cast. That is
     exactly the class of error the linter exists to catch.
  3. Windows consoles mangled the curly quotes and em dashes the model
     produces. The CLI now forces UTF-8 on stdout/stderr.
  4. There was no way to see what a run cost. Added token and cost accounting.
Both linter bugs now have regression tests, which is why the suite is 25 tests
rather than 19.

KNOWN LIMITS (honest list)
  * With no API key the mock prose is deliberately generic; judge the pipeline,
    not the paragraphs. With a key the prose is genuinely usable first-draft
    material that still needs a human editing pass.
  * No retrieval over canon source material - the bible is hand-written.
  * Single linear story per file; no branching drafts or version history.
  * Name detection in the linter is a heuristic. It reports "possible", not
    "wrong", and a legitimate new location or object will occasionally appear.
  * Context is not yet bounded: past roughly 20-25 chapters the previous-chapter
    tail plus bible will start to crowd the prompt. See Phase 2.
  * CLI only, no GUI. No streaming output.

4. TIME
-------------------------------------------------------------------------------
4a. THIS PROTOTYPE - already done
    Design, 1120 lines of code, 19 passing tests, demo run, this document:
    roughly 25 minutes of agent time in one session.
    A developer writing this by hand: 1 to 2 days.

4b. FROM PROTOTYPE TO SOMETHING PEOPLE USE
    Estimates are for one developer working with an AI agent. The "solo human"
    column is the same scope written by hand, for comparison.

    PHASE 1 - Make the writing genuinely good              agent 1-2 days
      Prompt iteration against real models, style samples  human  1-2 weeks
      ("write like this excerpt"), per-character voice
      locking, retry-on-weak-output, streaming so the
      user watches it write.

    PHASE 2 - Memory that scales past 20k words            agent 2-4 days
      Rolling summaries per chapter, an auto-updated       human  2-4 weeks
      timeline of established facts, embedding search
      over prior chapters, contradiction detection
      ("she was described as left-handed in ch3").
      This is the phase that decides if the product is
      real. Budget the most slack here.

    PHASE 3 - Interface                                    agent 3-5 days
      Web UI: side-by-side editor and chat, inline         human  3-6 weeks
      "rewrite this paragraph", accept/reject diffs,
      chapter reordering, autosave, AO3/EPUB export.

    PHASE 4 - Multi-user and safety hardening              agent 3-5 days
      Accounts, per-user projects, rate limits and cost    human  3-5 weeks
      caps, moderation on both input and output, audit
      log, ToS covering fan-work and platform rules,
      abuse reporting.

    PHASE 5 - Polish and launch                            agent 2-3 days
      Onboarding, docs, telemetry, error reporting,        human  2-3 weeks
      packaging (pip + installer), beta with ~20 real
      fanfic writers, fix what they break.

    TOTALS
      Prototype you can demo today ................ done (~25 min)
      Good enough for your own writing ............ +2 days agent / ~2 weeks human
      Shareable beta, web UI, no accounts ......... +1.5 weeks agent / ~2 months human
      Public multi-user product ................... +3 weeks agent / ~4 months human

    ONGOING COST (not time): MEASURED, not estimated. A real run on
    2026-07-27 produced a complete 4-chapter, 3665-word fic:

        8 API calls, 6575 input + 6678 output tokens, ~$0.016 total
          outline (4 chapters)     405 in /  434 out   ~$0.0003
          chapter draft, ~900 wds  ~800 in / ~1150 out ~$0.0008 each
          continuation, 250 wds    877 in /  407 out   ~$0.0004
          critique of a chapter   1609 in /  238 out   ~$0.0004
        Same chapter regenerated on gpt-4o instead of gpt-4o-mini:
                                   796 in /  984 out   ~$0.0118  (15x mini)

    So on gpt-4o-mini a full novel-length draft (~80k words, ~90 chapters)
    lands near $0.08. Even on gpt-4o it is roughly $1.10. API cost is not the
    constraint on this project; the constraint is prose quality and revision
    time. Spend the money on the better model.

    `show` reports cumulative spend per project, and every generating command
    prints tokens and estimated cost for that call. Prices live in
    providers.PRICES and need updating when vendors change them.

4c. IF THIS IS A SCHOOL PROJECT
    The prototype as it stands already demonstrates: architecture with clean
    separation of concerns, dependency inversion over the model provider,
    persistence, input validation, safety engineering, graceful degradation,
    and a real test suite. Phase 2 (memory) is the part worth writing up as
    original technical contribution - it is a genuine unsolved problem, not
    plumbing. Recommended scope for a term project: prototype + Phase 1 +
    a cut-down Phase 2 (rolling summaries and fact timeline, skip embeddings).

5. NEXT THREE THINGS I WOULD DO
-------------------------------------------------------------------------------
  1. Add a real API key and iterate the prompts in prompts.py until chapter
     quality is acceptable. Nothing else matters until the prose is good.
  2. Add rolling per-chapter summaries to the bible so context stays bounded
     as the fic grows past what fits in a prompt.
  3. Add `fanficai revise -c N --note "..."` for targeted rewrites - right now
     you can extend a chapter but not surgically change one.

-------------------------------------------------------------------------------
6. LEGAL / ETHICAL NOTE
-------------------------------------------------------------------------------
Fanfiction is generally treated as transformative fan work, but publishing
AI-assisted fic is contentious in fandom and some archives and communities
require disclosure or ban it outright. The prompts forbid reproducing long
verbatim passages from source material. If you publish anything from this tool,
check the destination platform's rules and label AI assistance honestly. This
is not legal advice.
